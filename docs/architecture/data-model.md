# Data model

The entities and their rules come from `docs/requirements.md` (section 6). This file shows how they are stored.

## Tables

One idempotent SQL file, `apps/api/src/store/schema.sql`, applied by `npm run db:migrate` (and by `npm run db:seed` and the database tests before they run):

```sql
create table if not exists resumes (
  id          uuid primary key,
  title       text not null check (char_length(title) between 1 and 100),
  text        text not null check (char_length(text) between 30 and 20000),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

create table if not exists vacancies (
  id          uuid primary key,
  company     text check (company is null or char_length(company) between 1 and 100),
  title       text not null check (char_length(title) between 1 and 100),
  text        text not null check (char_length(text) between 30 and 20000),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
```

- `id` is generated by the application with `crypto.randomUUID()`; there is no database default.
- The application trims `title`, `company` and `text` before validation and stores them trimmed. An empty company is stored as `null`.
- Lengths are counted in Unicode code points both in TypeScript (`[...value].length`) and in PostgreSQL (`char_length`), so the `CHECK` constraints never fire before the API validation.
- The application sets `updated_at = now()` in every `update`. Lists are ordered by `updated_at desc`.
- There are no relations between the tables. The planned `proposals` table will reference `resumes(id)`.

## In TypeScript

The store maps snake_case columns to the camelCase types of `apps/api/src/contract.ts`:

```ts
interface Resume { id: string; title: string; text: string; createdAt: string; updatedAt: string }
interface Vacancy { id: string; company: string | null; title: string; text: string; createdAt: string; updatedAt: string }
```

Dates are ISO 8601 strings in JSON.

## Neon branches

| Branch | Holds | Used by | Role |
| --- | --- | --- | --- |
| `main` | The user's own resumes and vacancies | Personal mode on the user's computer | Owner |
| `dev` | Fake data | Development in Personal mode | Owner |
| `test` | Whatever the tests create; the tests empty its tables | `TEST_DATABASE_URL`, database tests only | Owner |
| `demo` | Only the records of `data/seed.json` | The public demo (`DATABASE_URL` on Render) and `npm run db:seed` (`DEMO_DATABASE_URL`) | `SELECT`-only role for the demo, owner for the seed script |

The `SELECT`-only role is created once by hand in the Neon console, on the `demo` branch, after the first `npm run db:seed`:

```sql
grant usage on schema public to demo_reader;
grant select on resumes, vacancies to demo_reader;
```

## Seed

`data/seed.json` holds `resumes` (title, text), `vacancies` (company optional, title, text) and `samples` (a name, the title of a resume, and the company and title of a vacancy).

- The server reads it at startup. `GET /api/samples` resolves each sample to the full texts.
- `npm run db:seed` applies the schema and then, in one transaction, deletes all rows of the `demo` branch and inserts the seed resumes and vacancies with new ids. It connects only with `DEMO_DATABASE_URL`.
- The seed records are also the fixtures of the engine golden tests.

## Lexicon

`data/lexicon.json` is read and validated once at startup and never written by the application. Its format:

```json
{
  "lang": "en",
  "terms": [
    { "id": "kubernetes", "name": "Kubernetes", "aliases": ["k8s"] },
    { "id": "react", "name": "React", "caseSensitive": true },
    { "id": "state-management", "name": "State management" },
    {
      "id": "redux-toolkit",
      "name": "Redux Toolkit",
      "implements": [{ "term": "state-management", "source": "https://redux-toolkit.js.org/" }]
    }
  ],
  "headings": {
    "must": ["Requirements", "Required", "Must have", "Qualifications"],
    "nice": ["Nice to have", "Bonus", "Preferred"],
    "ignore": ["About us", "About the company", "Benefits", "What we offer"],
    "neutral": ["About the role", "About the job", "What you will do", "Responsibilities"]
  },
  "markers": { "must": ["required", "must", "essential", "mandatory"], "nice": ["plus", "bonus"] },
  "navigationLines": ["Show more", "Show less", "Apply", "Save", "Sign in to see who you know"],
  "fluffWords": ["passionate", "team player", "results-driven", "dynamic", "responsible for", "clean code"],
  "actionVerbs": ["built", "led", "migrated", "designed", "deployed", "cut", "shipped"],
  "negation": {
    "negators": ["no", "not", "never", "without"],
    "experienceWords": ["experience", "exposure", "knowledge"],
    "prepositions": ["with", "in", "of"],
    "phrases": ["never used", "have not worked with", "haven't worked with"]
  },
  "aspiration": { "phrases": ["currently learning", "plan to learn", "studying"] }
}
```

The values above are examples of the shape, not the final lists.

- `id`: lowercase slug, unique, never reused. `name` is what the UI shows.
- `aliases`: other spellings of the same term. `caseSensitive` (default `false`) applies to the name and the aliases.
- `implements`: one-hop relations to other term ids, each with a `source` link.
- The validator checks the rules of requirements section 6: valid shape, unique ids, no alias on two terms, every `implements` target exists, no `implements` cycles, no fluff word equals a term name or alias. It also rejects role names listed in the requirements (Full-Stack, Frontend, Backend, DevOps) as terms.
